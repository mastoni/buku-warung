# PR-10.1 — Commercial Provider Access / Authenticated Evidence Acquisition

## 1. Gate Scope
This gate focuses on acquiring authenticated/commercial evidence to resolve the blockers documented in PR-10. The objective is to verify live wholesale pricing, minimum deposit, refund/reversal terms, PPOB API existence (for Tripay), and commercial terms (for DANA) through legitimate means (e.g., provider documentation, dashboard access, or official communication) without entering production credentials, performing transactions, or modifying source code.

## 2. PR-10 Baseline
PR-10 concluded that no provider has sufficient verified technical AND commercial evidence for selection. Specific unresolved blockers:
- **Digiflazz**: Live wholesale SKU pricing, minimum deposit requirement, deposit/top-up mechanism, refund/reversal rules, commercial fees, account/KYC requirements, production vs. sandbox credential requirements.
- **Tripay**: Official PPOB/digital-goods fulfillment API existence (catalog, inquiry, create, status, callback), pricing/fees, commercial/access requirements.
- **DANA**: Commercial/reseller model, commission/pricing model, settlement mechanics, reserve/float requirements, onboarding/KYC requirements, API access requirements, and flow compatibility with Buku Warung's shop→provider model.

## 3. Evidence Acquisition Method
- Reviewed PR-9 and PR-10 documentation.
- Inspected the locked PR-8 `DigitalProviderAdapter` contract (no modifications).
- Attempted to access public provider documentation for any updates or additional commercial details.
- Sought authenticated access via provider portals where publicly available trial/demo accounts or sandbox credentials could be used without production credentials.
- No production credentials were requested, entered, or stored.
- No production PPOB transactions were attempted.
- All evidence collection adhered to the gate's evidence rules: prefer official documentation, distinguish public from authenticated, record source and date, avoid inference.

## 4. Digiflazz Authenticated/Commercial Evidence
- **Public Documentation Re-review**: Confirmed API structure for catalog, inquiry, create, status, webhook, and balance endpoints remains as documented in PR-9 (source: developer.digiflazz.com, accessed 2026-09-19).
- **Authenticated Dashboard Access**: No trial/demo account or sandbox credentials were publicly available for inquiry without registration. Registration requires personal/operational verification (KYC) and deposit account opening, which was not pursued to avoid entering a commercial relationship prematurely.
- **Verified Evidence**: None. All commercial terms (live wholesale pricing, minimum deposit, deposit mechanisms, refund/reversal window, fees) remain behind authenticated inquiry.
- **Unverified Evidence**: 
  - Live wholesale SKU pricing (price-list `price` values).
  - Minimum deposit amount and top-up channels.
  - Refund/reversal policy and time window.
  - Commercial/reseller agreement requirements.
  - Settlement/payment mechanics.
  - Production vs. sandbox credential requirements.
- **Conclusion**: Technical evidence from PR-9 remains sufficient for adapter compatibility, but commercial evidence is insufficient for selection.

## 5. Tripay Authenticated/Commercial Evidence
- **Public Documentation Re-review**: Confirmed developer documentation (tripay.co.id/developer) describes only payment-gateway APIs (virtual accounts, e-wallet, QRIS, convenience stores). No PPOB/digital-goods fulfillment APIs documented.
- **Authenticated Dashboard Access**: No evidence of a separate PPOB API in public merchant portal. Third-party library references (e.g., rick20/ppob) are unverified and contradicted by official documentation.
- **Verified Evidence**: None. Official PPOB/digital-goods fulfillment API does not appear to exist based on public documentation.
- **Unverified Evidence**:
  - Official PPOB API existence (catalog, inquiry, create, status, callback).
  - PPOB-specific pricing/fees.
  - Commercial/access requirements for PPOB line (if any).
- **Conclusion**: Tripay cannot be considered a digital-goods fulfillment provider without verified PPOB API documentation. Technical evidence for the required adapter contract is absent.

## 6. DANA Digital Goods Authenticated/Commercial Evidence
- **Public Documentation Re-review**: Confirmed DANA Digital Goods API (dashboard.dana.id/api-docs-v2) describes a reversed-flow model where DANA initiates orders to partner merchants.
- **Authenticated Dashboard Access**: No trial/demo account or sandbox credentials were publicly available for inquiry without registration. Registration requires partnership agreement and KYC on the merchant side.
- **Verified Evidence**: None. Commercial terms (commission rates, settlement timing, float/reserve model) require authenticated inquiry.
- **Unverified Evidence**:
  - Commercial/reseller model (whether Buku Warung can act as a partner/merchant).
  - Commission/pricing model.
  - Settlement mechanics and timing.
  - Reserve/float requirements.
  - Onboarding/KYC requirements.
  - API access requirements for production vs. sandbox.
  - Flow compatibility: Whether the partner-initiated/DANA-initiated flow can support Buku Warung's shop→provider model without architectural redesign.
- **Conclusion**: DANA's documented flow is incompatible with the locked adapter contract without inversion. Commercial evidence is insufficient to determine if a reversed-flow partnership could be accommodated.

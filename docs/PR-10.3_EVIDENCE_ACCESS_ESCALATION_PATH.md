# PR-10.3 — Evidence Access Escalation Path

## 1. Gate Scope
This gate establishes a controlled, auditable process for obtaining the authenticated/commercial evidence that remains blocked after PR-10.1 and reconciled by PR-10.2. It defines workflows for evidence acquisition without performing provider selection, implementation, or production transactions. The goal is to create a legitimate path to gather required evidence through proper commercial channels outside the Kilo gate system.

## 2. Source Baseline
- PR-8 `DigitalProviderAdapter` interface defines the locked technical contract (catalog, inquiry, create transaction, status check, balance, webhook).
- PR-9 established public documentation baseline for Digiflazz, Tripay, and DANA.
- PR-10 concluded no provider has sufficient verified technical AND commercial evidence for selection.
- PR-10.1 was BLOCKED and acquired no authenticated/commercial evidence.
- PR-10.2 reconciled that all material commercial blockers remain unresolved and provider remains NOT SELECTED.

## 3. PR-10.2 Blocker Summary
All material commercial blockers from PR-10 remain BLOCKED:
- Digiflazz: live wholesale SKU pricing, minimum deposit, deposit/top-up mechanism, refund/reversal terms, commercial fees, account/KYC requirements, production vs. sandbox credentials.
- Tripay: official PPOB/digital-goods API existence, catalog/inquiry/create/status/callback capabilities, pricing/fees, commercial/access requirements.
- DANA: commercial commission terms, settlement/reserve terms, onboarding/KYC requirements, API access requirements, flow compatibility with shop→provider model.

## 4. Evidence Acquisition Principles
- Evidence acquisition requires legitimate commercial engagement with providers (account registration, KYC, agreement) but stops short of production activation or transaction execution.
- No production credentials, API keys, or secrets will be requested, entered, stored, or committed.
- No production PPOB transactions will be attempted.
- All evidence collection must distinguish between PUBLIC, AUTHENTICATED, COMMERCIAL, and OPERATIONAL categories.
- Sensitive values (prices, fees, limits, credentials) must be redacted in any evidence documentation.
- Evidence must be sourced, dated, and contextualized.
- No inference will be presented as fact.
- The workflow does not authorize provider selection or implementation.

## 5. Evidence Classification
- **PUBLIC**: Official public documentation accessible without credentials (e.g., developer.digiflazz.com, tripay.co.id/developer, dashboard.dana.id/api-docs-v2).
- **AUTHENTICATED**: Documentation, dashboard information, or API details available only after legitimate account login (e.g., provider member area, developer portal post-login).
- **COMMERCIAL**: Reseller agreement terms, pricing structures, deposit requirements, settlement mechanics, refund/reversal policies, commission rates, fees, transaction limits, KYC requirements.
- **OPERATIONAL**: Onboarding procedures, account verification steps, support/contact methods, production activation requirements, SLA terms.
- **BLOCKED**: Evidence requiring access/relationship that is not currently available through legitimate means.

## 6. Digiflazz Access Path
1. **Account Registration Path**: Register as a buyer/partner at member.digiflazz.com (requires personal/operational verification - KYC).
2. **Authenticated Dashboard Access**: After registration, access the buyer-area/connection/irs to view:
   - Development IP / Production IP registration
   - Development Callback / Production Callback registration
   - API credentials (ID Mitra, User, Pin, Password, apiKey)
3. **Authenticated Documentation Access**: Log into developer.digiflazz.com to access:
   - Detailed API documentation behind login
   - Test case documentation for sandbox testing
   - Connection/IP whitelist requirements
4. **Commercial Evidence Request**: Through legitimate channels (support, account manager), request:
   - Wholesale price-list sample (with live `price` values redacted)
   - Minimum deposit amount and top-up channels (bank transfer, auto-deposit)
   - Refund/reversal policy and time window
   - Commercial/reseller agreement terms
   - Settlement/payment mechanics
   - Transaction limits/cut-offs (if any)
   - Production vs. sandbox credential requirements
5. **Evidence Handling**: 
   - Record source, date, and access context (AUTHENTICATED/COMMERCIAL)
   - Redact sensitive values (exact prices, credentials, personal data)
   - Do not store credentials or perform test transactions with real funds

## 10. Credential & Secret Handling
- **Prohibition**: No production credentials, API keys, passwords, tokens, or secrets will be:
  - Requested from users during evidence acquisition
  - Entered into any system during this gate
  - Stored in Android source code, resources, or assets
  - Committed to git in any form
  - Placed in documentation (even as examples)
  - Included in APK builds
- **Required Practice**: 
  - If credentials are obtained during legitimate evidence acquisition, they must be:
    - Used only in secure, approved environments (secrets management, vault)
    - Never committed, logged, or exposed
    - Rotated immediately after evidence acquisition concludes
    - Handled according to provider's security guidelines
  - All evidence documentation must redact:
    - API keys, secrets, passwords, tokens
    - Personal identity data (ID numbers, addresses)
    - Financial account details (bank accounts, wallet addresses)
    - Exact pricing/commission values (ranges or redactions acceptable)
    - Sensitive contractual terms

## 11. Commercial/KYC Boundary
- **Legitimate Evidence Acquisition**: Creating accounts solely to obtain legitimate documentation/evidence is permitted if:
  - No production capability is activated
  - No real transactions are attempted with real funds
  - Accounts remain in sandbox/test mode where possible
  - No financial commitment is made beyond minimal verification amounts (if required and refundable)
- **Production Activation Boundary**: 
  - Activating production capability (enabling real transactions, removing sandbox flags) is NOT authorized by this gate
  - Performing real PPOB transactions with customer funds is NOT authorized by this gate
  - Entering binding commercial agreements that obligate future purchases or payments is NOT authorized
- **KYC Participation**: 
  - Completing Know Your Customer (KYC) procedures for account verification IS permitted as part of legitimate evidence acquisition
  - Providing required documentation for verification IS permitted
  - Using verification methods that do not result in financial obligation IS permitted

## 12. Production Safety Boundary
- **Transaction Prohibition**: No production PPOB transactions will be:
  - Attempted with real customer funds
  - Attempted using production credentials
  - Initiated through the Buku Warung application
  - Simulated using real provider APIs with real money
- **Credential Safety**: 
  - Production credentials will never be:
    - Stored in shared preferences, databases, or files
    - Hardcoded in source code or resources
    - Transmitted over networks without encryption
    - Logged in any form (debug, crash, analytics)
  - If obtained legitimately, production credentials must be handled only in:
    - Approved secure storage solutions (secrets manager, encrypted vault)
    - Environments isolated from the source code repository
    - Systems with appropriate access controls and audit trails
- **Boundary Validation**: 
  - All evidence must be verifiable as obtained within these boundaries
  - Any evidence suggesting production transaction or credential misuse invalidates the acquisition path

## 13. Evidence Storage & Audit Trail
- **Storage Location**: Evidence (screenshots, documents, notes) must be stored:
  - Outside the source code repository
  - In access-controlled, audit-logged systems
  - With retention policies aligned to evidence validity periods
- **Audit Trail Requirements**: 
  - Each evidence item must record:
    - Source/provider name and specific document/screen
    - Date and time of acquisition
    - Access context (PUBLIC, AUTHENTICATED, COMMERCIAL, OPERATIONAL)
    - Method of acquisition (public URL, login to portal, support request)
    - Redaction details (what was redacted and why)
    - Validator/reviewer identity (if applicable)
  - Evidence log must be maintained and reviewable
- **Sharing Restrictions**: 
  - Evidence containing sensitive redacted information may be shared only with:
    - Authorized project stakeholders under NDA
    - Secure, auditable collaboration systems
  - Never shared in public forums, unsecured channels, or commit messages

## 14. Evidence Acceptance Criteria
An evidence item is accepted as valid only when ALL of the following are met:
- **Source Identification**: The provider and specific source (document URL, dashboard section, support ticket) are clearly identifiable
- **Date Recording**: The acquisition date is recorded (evidence expires if provider terms change significantly)
- **Access Context**: The evidence is classified as PUBLIC, AUTHENTICATED, COMMERCIAL, or OPERATIONAL with clear justification
- **Claim Support**: The evidence directly supports the claim being made (no extrapolation or inference)
- **Sensitive Value Handling**: 
  - Numeric values (prices, fees, limits) are either:
    - Published public values (acceptable as-is)
    - Redacted with range or category indication (e.g., "IDR XX,XXX - IDR XXX,XXX")
    - Clearly marked as sample/test data with disclaimer
  - Secrets/credentials are fully redacted or replaced with placeholders
- **No Inference as Fact**: 
  - Statements must distinguish between:
    - Verified fact ("Document states X")
    - Provider statement ("Provider claims Y")
    - Requirement ("To access Z, provider requires W")
    - Inference is labeled as such ("Suggests possible Z based on W")
- **Commercial Evidence Specifics**:
  - VERIFIED: Direct confirmation with unredacted proof (only for non-sensitive PUBLIC data)
  - PARTIALLY VERIFIED: Confirmation with redacted sensitive details or ranges
  - UNVERIFIED: No confirmation or conflicting information
  - BLOCKED: No access to attempt verification
